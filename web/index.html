ZERO-TRUST DESIGN

Three things the code enforces, not a policy

∑

A drawdown limit fixed in the contract

Every mandate's maximum loss from its high-water NAV is set once at launch and locked. No admin key can raise it later.

⚑

Anyone can enforce it, not just us

poke(), resume() and unwind() are permissionless. Whoever proves a breach first takes the bounty — operators have no special path.

◉

Every number here is a contract read

No backend database sits between this page and the chain. Every mark, trade and fee is a public event you can verify yourself.

BEFORE YOU ALLOCATE

Three questions worth asking

RiskGuard locks a maximum drawdown from the high-water NAV onchain. Cross it and anyone can call poke() to freeze new trades for a bounty — but a freeze stops further trading, it does not undo losses already marked. The limit bounds how much worse it can get; it is not a zero-loss guarantee.
There is no lockup fee, but there is a 1-day redemption notice: call requestRedeem(), then claim after the notice runs out. What pays out immediately is capped by the vault's cash on hand — the rest stays as shares until the agent frees up more cash.

    BATCHER ROLE

    Anyone can ask for settlement; only the batcher sends it

    The batcher only nets verified signed intents into one deposit per vault; it never chooses who gets how many shares — settleEpoch() recomputes the Merkle root from every signature itself. This demo's server plays the batcher, the same role deploy.mjs gives the deployer key on Monad.

    YOUR CLAIMS

    Settled, unclaimed shares

    Anyone may relay a claim; shares always go to the signed allocator, never the caller. Included intents and signatures become public in settlement calldata — this is a public batcher, not an anonymity set. The demo server keeps the claim proofs in memory, so claim soon after settlement: a server restart loses proofs not yet claimed.
